# 01 · Sign-in and roles

## Staff sign-in

- Page: `/login`. Email + password, with "Forgot password" sending a reset link by email.
- **Invite only.** Public sign-up is switched off in Supabase Auth settings.
- The CEO invites staff from `/admin/team`: name, email, role. The invite email links to a page where the person sets their password.
- After sign-in, staff land on their home area: CEO → `/admin`, account exec → `/accounts`, creative director and designer → `/creative`.
- The CEO can deactivate a staff member. Deactivated users can't sign in, and their past work keeps their name.

## Client sign-in by client ID

Clients sign in with a **client ID** and password. An email address is kept behind each login, used only for password resets and notifications.

**Client ID format:** `MM-` + 3 letters from the business name + `-` + 4 random digits, e.g. `MM-KGC-2611`.
- Generated by the app, unique, never reused, uppercase.
- Letters: the first letters of the first three words, or the first three letters of a one-word name, letters only.
- The client user record stores `client_code` (the shared business ID) and each user has their own `login_id`. The first user's `login_id` equals the client ID; extra users get a suffix: `MM-KGC-2611-2`.

**How sign-in works**
1. `/portal/login` takes login ID + password.
2. A server action normalises the ID (trim, uppercase), looks up the matching email with the service-role client (the only place this lookup is allowed), then calls Supabase `signInWithPassword` with that email.
3. Any failure (unknown ID, wrong password, deactivated) returns the same message: "That client ID and password don't match." No hint which part was wrong.
4. Rate limit: 5 failed attempts per login ID per 15 minutes, then a 15-minute lockout, with the same generic message. Store attempts in a `login_attempts` table (service role only).

**Creating a client login** (`/admin/clients/[id]` or the account exec's client profile)
1. Enter the contact's name and email.
2. The app creates the Auth user, the `client_users` row and the login ID, and sends a welcome email containing the login ID and a link to set a password. The password itself is never emailed or shown.
3. Normally done when the brand kit is signed off. It can be done earlier, so the client can follow onboarding.

**Password reset for clients:** "Forgot password" on `/portal/login` takes the login ID, finds the email server-side and sends the reset link. The screen always says "If that ID exists, we've emailed a reset link."

## Roles and access

Roles are stored in `profiles.role` (staff) or derived from `client_users` (clients). Write SQL helper functions and use them in every policy:

- `auth_role()` → the current user's role
- `is_staff()`, `is_ceo()`
- `can_access_client(client_id)` → true for the CEO, creative director and designers (all clients), for an account exec only when `clients.account_exec_id = auth.uid()`, and for a client user only for their own client

### Content status rules

One status runs through every content item and the brand kit, so everyone reads the same word:

```
planned → in_design → internal_review → client_review → approved → scheduled → published
                ▲              │                │
                └── changes_requested ◄─────────┘ (from internal review or from the client)
```

| Move | Who can make it |
| --- | --- |
| planned → in_design | Designer, creative director (also automatic when a timer starts) |
| in_design → internal_review | Designer, creative director |
| internal_review → client_review | Creative director only (this sends it to the client's portal) |
| internal_review → changes_requested | Creative director |
| client_review → approved, or → changes_requested | Client (in the portal), or the account exec on the client's behalf with a note saying how they approved |
| changes_requested → in_design | Designer, creative director |
| approved → scheduled → published | Account exec |

The brand kit uses the same flow up to `approved`, which is the client's sign-off. It records `signed_off_by` (name and role typed by whoever records it, or the client user's name when they approve in the portal) and `signed_off_at`.

Enforce allowed moves in a database function (`set_content_status(item_id, new_status, comment)`), not just in the UI. Every move writes a row to `status_events`.

## Area guards

- Middleware redirects anyone not signed in away from `/admin`, `/accounts`, `/creative`, `/portal` to the right login page.
- Each area's layout checks the role: `/admin` → `ceo`; `/accounts` → `ceo`, `account_exec`; `/creative` → `ceo`, `creative_director`, `designer`; `/portal` → `client`. The CEO can open `/portal/preview/[clientId]` to see exactly what a client sees, read-only.
- Wrong role → a plain "You don't have access to this area" page with a link to their own home.

## Acceptance criteria

- [ ] Public sign-up is off; an attempt to call sign-up directly fails.
- [ ] A client signs in with `MM-XXX-0000` and a password; a wrong ID and a wrong password show the identical message.
- [ ] Six wrong attempts on one ID lock it for 15 minutes.
- [ ] Password reset works for staff (email) and clients (login ID), and never reveals whether the account exists.
- [ ] Each role lands on its home area and is refused the others.
- [ ] SQL tests prove: an account exec cannot read an unassigned client's rows in any table; a client cannot read another client's rows in any table; a designer can read every client but cannot read invoices or leads; a client cannot read brand kit files before sign-off.
- [ ] Status moves outside the table above are refused by the database, and every allowed move writes a `status_events` row.
